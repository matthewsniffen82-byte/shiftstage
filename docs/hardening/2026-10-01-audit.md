# Hardening audit — October 1, 2026

Baseline: `dbff002ba952685700ec78baada01459fc6a9168`.

Follow-up: the owner requested more time for slow media transfers. The Internal
media deadline is now **240 seconds (four minutes)**, and the route's hosting
`maxDuration` is **300 seconds (five minutes)** to allow authorization and cleanup
headroom. The 45-second setting below records the original audit change.

This review combines current dependency advisories, selected security regressions,
source review of recent guest-list, Internal roster/media, and direct web-push
changes, and bounded read-only production checks. It is not an exhaustive
penetration test or a production load test.

## Findings and corrections

| Finding | Evidence and impact | Correction |
| --- | --- | --- |
| Vulnerable development dependency | `npm audit` reported `brace-expansion` 5.0.9 with two high-severity stack-exhaustion advisories and one moderate CPU-exhaustion advisory. The locked package is development-only; this review did not establish a remotely reachable application exploit. | Raise the override floor and lockfile to 5.0.12. Only this dependency changed. Add bounded child-process regressions for ordinary expansion, nested groups, and repeated rewrite input. |
| Internal media transport lacked resource limits | The authorized Internal route forwarded storage bodies without a byte ceiling or its own transfer deadline, followed redirects, and accepted arbitrary image response types. Malformed ranges were ignored. Two new route regressions fail on the baseline because unsafe responses and malformed ranges returned HTTP 200. Existing roster and media ownership checks still applied. | After authorization, enforce a 45-second signing/fetch/body deadline, 10 MiB image and 75 MiB video limits, raster/video MIME allowlists, redirect rejection, and cancellation on failure or consumer disconnect. Count actual decoded bytes even without a trustworthy length. Preserve authorized image fallback, video ranges, and private no-store responses. |
| Signing-secret boundary drift | Two server route handlers accessed the attribution signing secret directly instead of through the repository's server-only configuration module. The boundary inventory failed; no client-side secret exposure was demonstrated. | Route both reads through `getOptionalServerEnv`, retaining optional attribution behavior. |
| Security tests lagged retired APIs | Two assertions still expected upcoming-shift APIs, and the CORS inventory recognized only function declarations, missing exported handler variables and aliases. | Assert the current ownership-scoped reads and retired mutation responses; keep the public upcoming-shift compatibility field empty. Recognize function, variable, and named-export handlers, with a regression proving that aliased `OPTIONS` cannot escape the inventory. |

## Validation

- Initial selection: 768 tests, 764 passed and four failed. The four failures
  correspond to the signing-secret boundary and outdated assertions described
  above; all are resolved in the final selection.
- Final selection: **876 tests across 48 files passed**, with no failures,
  cancellations, skips, or todo. Coverage includes authentication and role/owner
  authorization, CORS and browser boundaries, public data minimization, request
  budgets, uploads, media access, cron/webhooks, SQL permissions and Storage,
  guest lists, Internal rosters, push delivery, and supply-chain controls.
- The new media tests cover slow signing, late headers after cancellation,
  stalled bodies, non-resolving cancellation hooks, oversized decoded bodies,
  dishonest/missing lengths, unsafe types, HEAD, valid/invalid ranges, fallback,
  and upstream failures. The route-level regressions also pass through existing
  active-table/staff and media-ownership checks.
- Focused TypeScript checking of the changed routes/helper and their imported
  dependencies passed. Its first process ran out of memory; the retry with an
  explicit 2 GiB Node heap completed successfully. Changed-file ESLint passed
  with zero warnings.
- Fresh `npm audit`: **zero known vulnerabilities**. Registry verification:
  **382 signatures and 57 attestations verified**.
- Runtime verification passed on Node 24.21.0 and the pinned FFmpeg binary,
  including its synthetic encoding check.
- Read-only production document/header checks: **23 requests passed**. This
  includes private-document nonces/cache policy, callback policy and CORS.
- Read-only Supabase readiness: **63 checks passed**, including protected
  columns, public projections, Storage policy and required schema/function
  presence. These checks do not prove every production row-level policy outcome.
- The migration provenance guard passed. Historical replay remains quarantined
  as designed; this audit applies no SQL. The unrelated untracked migration and
  concurrent design work are excluded from this change.

Evidence logs and the exact selected test list are retained locally under
`tmp/hardening-audit-2026-10-01/`. The final delivery receipt in that directory
records the pushed revision, matching Git refs and exact Vercel result separately
from the production-alias health check.

## Limits

No hosted private-account browser journey, real notification/payment delivery,
hostile production upload, stress test, backup restore, or complete automated
suite was run. Production probes were read-only; database behavior tests used
synthetic fixtures. The new media limits bound an individual transfer, not total
concurrent traffic or application capacity. Dependency results describe the
registry's known advisories at review time. These results do not certify the
absence of vulnerabilities elsewhere in the application.
