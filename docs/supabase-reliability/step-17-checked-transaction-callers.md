## Resulting behavior

Request-information, reject, court-hold and close actions use the administrator transition function. The panel sends the displayed case's timestamp without rounding PostgreSQL's fractional precision. The transaction checks that version and the current status while locking the case, then commits the case and audit together. A stale screen receives a conflict. The panel offers a read-only refresh that preserves the administrator's unsaved case notes and agent form, and prevents duplicate actions during loading or an active request.

The caller checks the returned case identity, intended status and finite timestamp before reporting completion or sending a completion email. Missing, malformed or lost transaction receipts require a state review. It does not retry the transaction or send completion mail after an unconfirmed result. A confirmed action remains complete when optional email fails; the response separately requires delivery review.

After the mail provider acknowledges counter-notice forwarding, the caller uses the forwarding transaction. That function validates the case/counter relationship and the allowed states. The caller accepts a checked forwarded or completed receipt, preserving a completed status. An uncertain acknowledgement receives one read-only reconciliation attempt. It does not resend mail within that attempt. This is not a durable outbox or an exactly-once email guarantee; terminal history and provider reconciliation remain Step 19 work.

Profile publication uses one transaction call. It no longer falls back to a separate read/update sequence when the function is missing or unavailable. Returned identity, status, verification, visibility, timestamps and the requested transition are checked before completion is reported. A retained administrator suspension remains disabled/private when the owner requests reactivation. Copyright and later independent publication restrictions remain enforced by the deployed database functions.
