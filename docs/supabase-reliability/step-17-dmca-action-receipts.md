# Step 17: confirm copyright actions independently of email delivery

## Reproduced defect and bounded correction

The current service accepts a null or mismatched successful RPC response from `apply_dmca_takedown` or `restore_dmca_case`, reports the requested action complete and may send completion emails. The scheduled worker likewise increments its restored count after a null receipt. A thrown email or uploader lookup can instead turn an already committed action into an apparent action failure. These behaviors were reproduced by executing the actual service with local synthetic transports; no real case, provider operation or email was used.

Validate the receipt against the selected case, target and uploader, require finite nonnegative integer strike counts and the correct restoration/enforcement outcome, and return only explicitly checked fields. Takedown requires a recorded strike and target/uploader identity; restoration retains the existing nullable identities used by retained cases after deletion. A case initially lacking an uploader accepts the transaction's valid resolved uploader. Case IDs are normalized before lookup and comparison. An absent, malformed, mismatched or uncertain receipt produces a typed 503 response or an unconfirmed worker result. Each request invokes the business RPC once, sends no completion mail for an unconfirmed outcome and directs the operator to review current state before trying again.

After a confirmed receipt, attempt each existing email once. A false/missing provider acknowledgment, thrown provider error, unavailable uploader email lookup or invalid recipient address sets `deliveryNeedsReview`; it does not erase the confirmed action or prevent the other recipient's attempt. Administrator responses expose `partial` with a message that keeps the completed action explicit. The existing panel displays this server message and refreshes case state. The worker counts confirmed restoration separately from its email outcome. Diagnostics use the existing safe-error metadata filter and exclude legal details and email addresses.

## Evidence and limits

Focused tests run the actual TypeScript service and administrator/worker HTTP handlers with synthetic database and provider boundaries. They cover malformed identities, counts and outcomes, returned/thrown uncertain writes, no repeat mutation, independent email attempts, lookup failure, retained deletion nulls, resolved uploader identity, checked-field projection, exact verified administrator actor use, authorization rejection before privileged-client creation and per-case worker continuation. Real authorization policies retain their existing release-suite coverage; the HTTP fixtures replace the authentication boundary deliberately. No native database transition or hosted multi-connection coverage is claimed by these caller tests.

This release changes no SQL, public permissions, statutory eligibility calculation, counter-notice forwarding policy or database notification/audit transaction. It does not add a durable email outbox or claim exactly-once delivery. A confirmed SQL receipt establishes the existing transaction's reported outcome; it cannot prove that the legacy transaction preserves unrelated later lifecycle decisions. Cross-case content/account ownership, later manual decisions, repeat-strike release and court-hold races remain under Step 17 review, with provider recovery in Step 19. Existing hosted account/mail, independent-connection and restore/history exercises remain deferred by the user.

Complete combined tests, TypeScript, lint, dependency/signature/runtime checks, production build, actual configured private-value artifact inspection, exact source proof, commit/push, exact Vercel success and deployed read-only health/readiness remain release gates. No production takedown, restoration, email or record mutation is required for verification.
