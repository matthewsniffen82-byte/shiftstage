## Finding and correction

The current `validate_sales_agent_hierarchy()` checks self-sponsorship, active sponsor admission and recursive cycles for each inserted or updated row. It does not serialize writers to different agents. Concurrent A→B and B→A changes can each inspect the other's earlier root state; row-local checks do not establish that their combined result is acyclic. The 05:58:07 UTC read-only preflight on September 12 found zero agents, active attributions and cycles. This is a code-based concurrency finding, not an observed live financial incident or a completed independent-session reproduction.

Add one invoker function and a BEFORE STATEMENT trigger for sales-agent INSERT and UPDATE OF sponsor_agent_id,status,commission_depth_limit. It acquires the common transaction advisory lock before that statement modifies or locks individual rows. The existing row validator, account checks, active-founder uniqueness and all other constraints remain intact. The helper validates its table/event/statement context, uses a pinned path, bounds its lock wait to three seconds and has no API EXECUTE grant. No new table or application record is created by migration.

The statement trigger also covers upserts and statements that find no rows. Repeated acquisition within one transaction uses the same lock, and commit or rollback releases it. Under Read Committed, the existing volatile validator's subsequent queries obtain fresh visibility after the wait. Repeatable Read hierarchy writes are rejected because an earlier snapshot can conceal a committed change; Serializable remains supported with PostgreSQL's serialization checks. These choices follow PostgreSQL's documented [trigger timing](https://www.postgresql.org/docs/17/trigger-definition.html), [function snapshot behavior](https://www.postgresql.org/docs/17/xfunc-volatility.html) and [transaction advisory locks](https://www.postgresql.org/docs/17/explicit-locking.html). Their application to this graph is the design reasoning; hosted multi-session tests remain deferred.

The two attribution writers currently lock the signer, then read up to five ancestors in separate statements. Replace that sequence in `assign_admin_venue_sales_agent()` and `attribute_approved_venue_agent_referral()` with one bounded recursive SQL statement. It records the five sponsor levels from one statement snapshot while retaining the locked signer's parent. It preserves the existing authorization, signer state, active venue checks, effective-time ordering, unique active attribution, immutable prior attribution values, required audit and return behavior. Ancestor changes after capture do not rewrite the stored attribution.

Attribution readers do not take the new hierarchy lock. In particular, adding it inside the venue-approval AFTER ROW trigger would introduce a graph/venue lock-order interaction with the earlier manager-activation trigger. The single snapshot query avoids this extra reader lock. Existing commissions, rate/depth eligibility, signer IDs, amounts, historical snapshots and the stable `agent_allocations_for_venue()` function remain unchanged.
