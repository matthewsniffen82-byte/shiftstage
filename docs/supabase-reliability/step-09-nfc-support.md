## Issue and controlled plan

`POST /api/venue/nfc-support` inserts the NFC request, then creates its support message in a separate transaction. If the latter result is uncertain, it deletes the request even though its message may already exist. A successful message followed by a response failure can also cause a repeat request. The existing `create_support_message_safely` function already handles its thread, message, in-app notifications and per-account send limit atomically; reuse it without rewriting that working helper.

First add an unused service-only security-invoker `create_venue_nfc_support_safely` function. It must validate active venue accounts, current owner/team access and tag assignment inside the transaction, then insert the request and call the existing support-message function. A failure in either rolls back both. Keep external delivery and optional venue activity logging outside this database transaction. The later caller release must preserve their existing behavior and report only confirmed request fields.

Use an explicit request UUID as the existing request primary key and support message primary key. Replaying that key with the same actor/venue/tag/type/notes returns the original linked request without rewriting its status or generating duplicate messages/notifications. A conflicting key or broken prior linkage must fail without overwrite or deletion. Different intentional requests remain distinct. The later UI/caller release must retain one key for an unchanged submission across a transient failure and use a fresh key for changed/new input; legacy callers without a key can receive a server-generated key.

Keep the original support permissions: active venue owner, manager or staff; inactive accounts/owners, removed membership and tags assigned elsewhere are denied. Preserve the existing ability to request support for a disabled/revoked assigned sticker and an unpublished venue. Lock involved account rows in deterministic order before venue/tag rows, matching account-before-venue lifecycle ordering; bound lock waits. Recheck venue ownership after acquiring locks, and serialize same request keys. Do not trust actor role, venue name or sticker labels supplied by the caller.
