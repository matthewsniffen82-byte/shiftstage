# Step 11: gallery retirement foundation

## Inspected risk and bounded plan

Photo/avatar removal and avatar replacement can physically delete an image another gallery/avatar still references. The gallery publication cleanup checks current references but releases that protection before deleting storage; a concurrent publisher can add a reference in between. Existing reference history is evidence, not deletion authorization.

Prepare an additive, initially unused service-only retirement RPC with a private permanent marker and restricted reference triggers for `dancer_photos.storage_path`, `dancer_profiles.avatar_storage_path` and `image_moderation_records.final_storage_path`. Serialize a retirement with new references to the same image family. Refuse retirement while any of those sources refers to the master or a stored responsive variant, and require a matching profile's durable reference history. Once retired, refuse new references to that family; repeated retirement returns the same receipt. No physical storage operation occurs in this migration or RPC.

Only canonical gallery master paths qualify for retirement. Retain unrecognized, external, nested or variant-only paths for separate reconciliation. Keep all old migrations, business rows, source columns/constraints/indexes/policies, history and functions unchanged. Add source triggers without replacing the history writer. No current application cleanup caller changes until this foundation is independently tested, committed, pushed, applied through a guarded wrapper and deployed/verified.

The guard uses transaction-scoped advisory locks and separate fresh reads in VOLATILE functions. PostgreSQL documents [fresh statement snapshots for VOLATILE functions](https://www.postgresql.org/docs/17/xfunc-volatility.html) and [transaction-scoped advisory locking](https://www.postgresql.org/docs/17/explicit-locking.html). Explicitly reject non-Read-Committed transactions for new nonempty references/retirement, because a fixed older snapshot must not be mistaken for current absence; ordinary clearing/removal remains possible. This restriction must be tested and documented, not silently assumed. Unchanged references return before locking. AFTER INSERT/UPDATE guards inspect the final stored path, including any changes introduced by another trigger.

Run full tests, lint, production build, standalone TypeScript, migration checks and read-only readiness; commit/push only this foundation, apply its exact committed migration, verify preservation/security and exact Vercel/health before changing callers.

No production retirement, upload or delete is a test. Hosted multi-connection contention remains deferred; isolated sequencing/rollback tests and documented locking semantics are not reported as a hosted concurrency pass. The marker must remain after failed/partial storage deletion so that a retry cannot race republication. Never delete markers to repair an error. A rollback before any claims can remove only these additive objects in a reviewed migration; after claims, retain markers/guards and use a forward fix. Failed upload-attempt recovery and non-gallery storage remain separate work.
