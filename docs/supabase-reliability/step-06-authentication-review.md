## Current lifecycle and evidence

| Boundary | Current behavior and regression coverage |
| --- | --- |
| Signup and duplicate email | Auth route bounds credentials, uses provider signup and the canonical provisioner, preserves exact passwords, sanitizes provider rejection and respects confirmation-only responses. Duplicate/partial provisioning and the older unused helpers require Step 7; a provider user alone is not proof of a usable application profile. |
| Login and session restoration | Password verification comes from Supabase; the account role comes from the database. Active role gates remain on privileged operations. Browser session ownership and login/refresh ordering guards prevent delayed responses from overwriting a newer sign-in or logout. |
| Expiry and provider failures | Request authentication verifies the provider user after any refresh. Bounded fetch prevents unbounded SDK retry loops and converts ambiguous infrastructure failures into temporary errors. Existing tests distinguish rejected credentials from 408/429/5xx and network failures. |
| Confirmation and recovery callbacks | OTP/code exchange delegates to the provider; fragment sessions require server verification. Callback responses scrub credentials, use no-store/no-referrer and a restrictive CSP, retain local return-path validation, and preserve an unrelated sign-in when a link is invalid. Recovery cannot borrow an ordinary stored session after a failed link. |
| Password-reset delivery | The endpoint rate limits before requesting email, returns neutral success wording, and reports delivery failures as unavailable. No reset email is sent by the audit. |
| Password update | The server verifies the account before updating credentials. Other-session revocation and email notification failures cannot falsely report that the password was unchanged. The form now sends the exact captured token pair and shows the returned revocation warning only after a confirmed password update. No automatic credential-write retry was added. |
| Logout | Local state clears immediately; the server validates the caller and asks the provider to revoke the local session. An already-issued access JWT can remain valid until expiry, so current database account/role checks remain essential. |
| Account changes/deletion | Authenticated email changes retain secure provider confirmation; account state/deletion protections remain intact. Multi-step deletion and profile provisioning recovery are explicitly assigned Steps 7, 9 and 17. No live deletion or account modification was performed. |
