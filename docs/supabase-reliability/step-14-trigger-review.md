## Confirmed defect and bounded correction

`enforce_mydancr_tv_profile_video_limit()` exists with the intended fifty-video limit but has no attachment. `mydancr_tv_videos` has only the review-decision and venue-link triggers. The historical July migration creates the missing attachment; the later August capacity migration only replaces its function body. Neither version is in the current ledger, and the collided August distribution version tracks a different finance migration. No later repository migration explicitly removes this video attachment. These facts establish current drift, not a safe historical replay plan.

The application and upload/import callers still intend fifty current profile videos. Their count and insert are separate requests. Native PostgreSQL reproduces 51 reservations against the captured current schema. The production aggregate preflight at 05:12:57 UTC found 34 videos, zero profiles above fifty, and a maximum of four occupied slots. It returned counts/fingerprints only. No production video was inserted, restored, moved or deleted as a test.

The additive migration replaces this one invoker function and adds one `AFTER INSERT OR UPDATE OF dancer_id, distribution_scope, status` row trigger. It counts uploading, moderating, submitted, approved and rejected profile videos, including the final inserted/updated row. It leaves feed-only, hidden and expired videos outside the count. A transition within an already occupied slot remains allowed; restoration, feed-to-profile changes and transfers must claim destination capacity. Ignored conflict inserts consume no slot, and idempotent updates continue to work at capacity. Existing rows are retained, including hypothetical pre-existing excess rows, while expansion is rejected.

The transaction takes one advisory lock per destination dancer before a separate count query. Read Committed obtains a fresh snapshot after the wait; Serializable relies on PostgreSQL serialization checks. Repeatable Read is explicitly rejected for a new slot because its earlier snapshot could conceal a committed reservation. Existing-slot edits and slot releases remain possible. No current application path requests Repeatable Read for video writes. Native tests establish lock identity, lifetime and per-dancer separation; independent hosted-session concurrency remains deferred and is not claimed tested.

The AFTER timing observes the final row and avoids rejecting ignored `ON CONFLICT` inserts. It executes within the original transaction, so capacity rejection also rolls back the row and any earlier side effects. The existing venue-link validation, moderation notification and audit trigger stay installed unchanged. See PostgreSQL's [trigger behavior](https://www.postgresql.org/docs/17/trigger-definition.html) and [SPI visibility rules](https://www.postgresql.org/docs/17/spi-visibility.html).
