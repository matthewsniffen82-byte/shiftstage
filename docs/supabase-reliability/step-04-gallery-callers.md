# Atomic gallery publication callers

The automatic upload, retry worker and administrator approval paths now call `publish_approved_dancer_gallery_photo`, introduced in `4fed8cb7`. The transaction chooses the final position and saves the photo, approval and profile status together. Two additions that request the same position retain both photos. Legacy moderation records can add photos but cannot infer replacement permission from a position.

New uploads persist explicit add/replace intent. Replacement requires the selected photo ID, checked against the authenticated dancer's profile before moderation and checked again inside the publication transaction. The legacy editor captures this ID before opening the crop dialog. A concurrent change cannot silently redirect replacement to the newer photo occupying that position. Old clients without a replacement ID receive a refresh instruction; additions continue normally. A pending review must be removed before uploading a replacement for that pending item.

The caller sends the exact moderation version it evaluated. Retries use the timestamp written by their status transition. Stale administrator rejection, automatic status updates and pending-photo deletion use conditional writes; they cannot overwrite or delete a committed approval. A duplicate upload key returns the existing record. Successful repeat approvals return the committed photo identity. Potentially referenced files survive lost responses, and predecessor storage cleanup starts only after the transaction is acknowledged.

This caller release changes no SQL, policies, grants or production media directly. Read-only production verification found migration `20260909203842` applied once, its publisher present, and normalized SQL SHA-256 `819e7b9651aacb26fa480416b1ec67c23f331feddfceb53e64b7584065e63301`, matching the committed migration. The foundation's exact Vercel deployment succeeded. Existing zero-order photos remain intact; no unique index or data renumbering is added.

Tests execute the actual SQL transaction and automatic/admin application callers against synthetic PostgreSQL fixtures. They cover competing additions/replacements, identity and ownership, library limits, moderator permissions, stale decisions, cancellation races, atomic rollback and lost responses. Browser-side tests verify replacement identity survives changes during cropping and reaches the API. Existing avatar, image recovery and mobile/media coverage remains in the complete suite. PGlite queues statements within one instance; this is not a multi-connection Supabase load test. No production upload or approval is used as a test.

Known follow-up work: reconcile retained unused storage only after checking references and operation outcomes; review legacy media writers before adding uniqueness constraints; complete the separate cross-role/RLS audit. Concurrent pending uploads can temporarily share a displayed provisional position until publication assigns final positions. Full historical migration replay remains deferred by the user. Do not roll back to slot-based replacement as routine recovery.

The release is complete only after full tests, lint, standalone TypeScript, production build, exact-commit Vercel success and post-deployment checks. Final commit and deployment evidence are recorded in the external review report.
