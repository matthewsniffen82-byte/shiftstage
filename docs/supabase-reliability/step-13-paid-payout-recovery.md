# Step 13 — paid payout recovery transaction

The inspected `reverseDancerPayoutTransfer` handler authenticates Stripe delivery and matches a persisted provider reference. For a paid or partially reversed transfer it separately updates paid earnings and inserts a financial audit. A failed audit can leave an unaudited flag; a retry can duplicate the audit; the update does not acknowledge affected rows and replaces an existing review reason. This does not justify automatically debiting or repaying anyone.

Plan: first deploy an additive service-only RPC that locks the exact paid Stripe payout, verifies its paid earnings and payout-item relationships, sets recovery flags and writes the audit in one transaction. Preserve existing review reasons, balances, paid status, provider references and every unrelated earning field. Require exact write acknowledgments and return a same-payout retry receipt after a confirmed prior audit. Existing flags without an audit must gain the missing audit. Use the existing target index for the bounded audit lookup.

This foundation does not switch the caller. After its test/commit/push/deployment/verification gate, a separate correction will use the RPC from the signed webhook flow and validate its receipt. Completion of a partial transfer remains a separate existing operation; failures must stay retryable without releasing paid earnings for another payout.

Validation uses isolated PostgreSQL with the already inspected financial schema and actual payout creation/completion functions. Test cross-reference errors, stale states, unexpected write receipts, audit failures, repeated delivery and denied roles. Do not invoke the new RPC or transfer/reversal operations against production. Hosted concurrent connections remain deferred.

The migration adds only a function and service execution grant. It changes no existing rows, columns, constraints, indexes, functions or policies.
