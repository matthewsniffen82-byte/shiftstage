# Step 24: CI and supply chain

## Finding and correction

The repository had no GitHub Actions workflows or runs, no rulesets, and an unprotected main branch in the readable branch metadata. Vercel ran only `npm run build`, so its automatic deployment did not independently require the complete automated suite, standalone TypeScript or full lint. The existing local delivery procedure did require those checks, but the deployment command did not enforce them.

This release adds a common `verify:release` command and makes it Vercel's configured build command. It rejects an npm version different from the exact `packageManager` pin, audits all installed dependencies for known advisories, verifies npm registry signatures, checks the Node/native FFmpeg runtime, refreshes generated assets, runs the complete test suite with two workers, generates Next route types for a fresh checkout, runs standalone TypeScript and full lint, then runs the existing production build. Any failed stage prevents later stages and fails the deployment. The existing prebuild migration guard and postbuild maintenance rules remain in place.

The check subprocesses receive an allowlist of operating-system path/home/temp variables and synthetic public Supabase settings. Provider credentials, inherited Node preload options, npm lifecycle-bypass settings, production flags and optional baseline-test flags are excluded. This is process-environment minimization, not an operating-system or network sandbox: tests still execute trusted repository code with the checkout's file permissions. Local environment files must not be mistaken for isolated staging. The clean-checkout verification and GitHub jobs contain no production environment files or credentials. Only the final Vercel build receives its existing deployment environment; this preserves its configuration validation and explicit maintenance behavior.

Vercel validates direct pushes to main. GitHub validates code pull requests targeting main on Ubuntu 24.04, with an optional manual dispatch covering Ubuntu and Windows Server 2022. Documentation-only pull requests do not start the GitHub suite. There is no duplicate GitHub push job. The workflow has only `contents: read`, persists no checkout credentials, uses no repository secrets, disables automatic package-manager caching, and pins the two official actions to full commit IDs verified against their release refs. It does not use privileged pull-request events, event data in shell commands, artifact promotion or deployment credentials. Concurrent obsolete runs are cancelled and jobs have a 40-minute limit. There is no recurring schedule.
