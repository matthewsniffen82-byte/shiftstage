## Confirmed finding

**MEDIUM — unfinished deliveries acknowledged as completed duplicates.** The atomic claim returns false for both a processed event and an unexpired processing lease. The handler previously acknowledged both with HTTP 200. If a worker crashes and Stripe redelivers during its existing ten-minute lease, the successful duplicate response can suppress further retry before the event becomes reclaimable. This requires a genuine signed delivery; it is not an unsigned payment-forgery finding.

The application now accepts only explicit boolean claim results. A false claim reads only `processing_status`, scoped to the exact provider/event pair, and acknowledges only `processed`. In-flight, failed, missing, unreadable and unrecognized states return the existing generic HTTP 500, retaining provider retry. True claims keep the existing processors. Finalization now requires a returned record ID; a zero-row/unconfirmed update cannot report delivery success. No immediate automatic retry, financial mutation, credential change, lease change or database migration is added.

## Seventh bounded release: partial payout reversals

**LOW in the currently disabled integration — a partial transfer reversal releases the full pending reservation.** Stripe's [transfer model](https://docs.stripe.com/api/transfers/object) permits amount_reversed smaller than amount, with reversed still false. The existing webhook ignored both amounts and used the full-release function whenever the local payout was not paid. A genuine partial reversal arriving before the created-transfer callback could therefore make the whole reserved earning available again. If payouts were enabled and the earning became eligible for another batch, this could overpay it. Read-only production inspection at 03:31:03 UTC found no payout batches/accounts/subscriptions and payouts disabled; no active exploitation or live payment loss is claimed.

The route passes the signed transfer object to the existing reversal gateway. Positive safe integer amounts, bounded by the original transfer amount, are required before financial work. A partial reversal for a nonterminal payout confirms the original transfer through the existing completion gateway and then uses the existing paid manual-recovery flags/audit. It cannot release the entire reservation. The original transfer creation time supplies the payment timestamp and must be valid before completion. An already-paid partial reversal uses recovery directly. An already-released exact transfer remains unchanged, and full reversals retain the existing release/paid-recovery behavior.

There is no new provider call, automatic debit, payout enablement, schema or permission change. A missing or uncertain completion keeps the failure/retry behavior; it never falls back to release. A concurrent full release stays terminal; a concurrent payment is confirmed before recovery. Completion, recovery flags and audit insertion remain separate operations: an interrupted delivery returns failure and an explicit signed redelivery completes the existing paid-recovery path. This release does not claim global transactionality across those operations or deduplicate existing recovery audit entries.
