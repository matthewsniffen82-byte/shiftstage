## Public and private boundaries

The thirteen public shift columns are `id`, `dancer_id`, `venue_id`, `starts_at`, `ends_at`, `timezone`, `status`, `location_status`, `checked_in_at`, `checked_out_at`, `location_verification_expires_at`, `shift_date` and `shift_source`. These support intentionally published schedules and presence. Venue addresses and venue map coordinates describe the public business location.

The newly protected columns are `created_at`, `updated_at`, `checkin_distance_feet`, `last_location_verified_at`, `working_status`, `venue_affiliation_id`, `nfc_tag_id` and `nfc_last_tapped_at`. Existing device coordinates, accuracy, financial and internal summary fields remain protected. Neither the migration nor validation reads real device-location rows into the client.

The existing `has_active_club_deal(venues)` helper is a computed boolean field over a venue row. Its argument is unnamed, so it is not a standalone PostgREST RPC. The earlier Step 26 phrase “browser-callable function” referred to database EXECUTE permission and was too broad as an HTTP exposure description. The boolean does not return the deal payout amount or rules. [PostgREST computed fields](https://docs.postgrest.org/en/stable/references/api/computed_fields.html).

The venue restriction protects `created_at`, `updated_at`, `qr_code_storage_path`, `qr_code_label`, `qr_code_updated_at`, `page_review_status`, `page_review_sent_at`, `page_reviewed_at`, `page_reviewed_by_user_id` and `page_review_notes`. Public business contact/location, hours, active/publication state and public cover/logo fields remain selectable. The opaque `owner_user_id` also remains selectable: existing RLS predicates on related deal, finance and team tables depend on it. A native before/after experiment proved that removing this grant breaks related role queries; restoring only that grant preserves their previous results. This release does not claim owner-identifier confidentiality. Replacing that predicate dependency and restricting the identifier is an explicit Step 28 followup, with its own policy tests and deployment. Existing row visibility policies and service SELECT remain unchanged. The native experiment confirmed that column restriction also denies anonymous/authenticated whole-row computed-field selection. Current public discovery/profile/TV routes already use the server client. Saved customer follows and going records retain their request-client ownership checks, omit the computed field from those joins, and resolve only the referenced venue IDs through bounded server queries. Public schedule hydration uses the same existing server client. Professional review/ownership routes already authorize server reads. No computed-function rewrite or broader private customer read is introduced.

## Account transition and recovery semantics

`account_self_pauses` has no browser read/write policy or grants. Explicitly removing default service privileges before granting CRUD avoids accidentally adding TRUNCATE, REFERENCES or TRIGGER authority. The transition has only service EXECUTE permission, a fixed empty search path and a three-second lock timeout. The authenticated account route supplies the target user ID. Browser input cannot choose another account or the caller's role.

The transaction locks the account, its owned venue or dancer profile, then the private pause record. It inserts restoration ownership after its own pause writes. Resumption captures that ownership under the same locks before the account update invalidates it. A venue team member's personal account operation does not affect the venue owned by someone else. Permanent deletion still clears public account name/email and hides owned publication; the route then performs the existing Auth identity deletion. An Auth deletion failure remains a separately reported incomplete login deletion.

Old immutable deployment URLs may continue receiving requests after a new release. The observed Vercel maximum function duration does not prove those URLs are retired. The same database transaction therefore removes direct service-role UPDATE of `app_users.account_state` and `venues.is_active`, retaining UPDATE on the other seven account and twenty-nine venue columns. This blocks both old direct account writes and old compensating venue writes. Legitimate venue removal/publication/review callers use `change_venue_publication_safely`, which locks and rechecks active administrator/owner/manager authority, expected review state and requested fields. Ordinary venue edits keep their existing path. The deployment wrapper locks account/venue/profile tables and Auth metadata during bootstrap; it does not rely on a delay or deployment-URL expiry.

Existing trusted, disabled, unrestricted self-pauses require a bounded compatibility import. The old system did not durably record profile/venue visibility ownership. Imported pauses therefore preserve login resumption without automatically republishing old content; an eligible dancer is restored privately and can explicitly publish afterward. Existing Auth metadata is neither changed nor used as ongoing restoration authority. Fresh aggregate counts must establish which legacy roles are actually affected before applying the migration.

A later administrative or copyright account restriction revokes an earlier self-pause permission. If a subsequent copyright restoration returns the account to its prior **disabled** state, it does not recreate that revoked permission. Self-service remains blocked pending an explicit support decision. The application has an administrator dancer-profile restoration endpoint, but it does **not** provide a general endpoint to restore `app_users.account_state`. Do not describe profile restoration as login-account recovery. See the operator procedure below; no production recovery action is performed as validation.

## Explicit recovery procedure

1. Receive and verify an account recovery request through the existing support process. Record the authenticated administrator/operator's approval and reason. A cleared copyright hold alone is not approval to override another restriction.
2. Read the exact account, relevant copyright state and private pause record using authorized operator access. Confirm identity, `account_state = disabled`, no current copyright hold, and no later administrative restriction. Stop on ambiguity; never recreate a pause from a historical Auth timestamp.
3. An authorized database operator may perform a separately reviewed, bounded transaction targeting that exact account with expected-state conditions, record the decision in the existing administrative audit table, and set the login account active. Keep venue/profile visibility unchanged. Verify one account row and one audit record; roll back on any mismatch. This procedure is not an automatic endpoint, a bulk repair, or authorization to execute it during this security audit.
4. If publication also requires restoration, make a separate explicit review through the existing dancer/venue administrative workflow. Do not infer prior public visibility or clear unrelated moderation restrictions as part of login recovery.
