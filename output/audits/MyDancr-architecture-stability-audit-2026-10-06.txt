FINDINGS IN RECOMMENDED FIX ORDER

1. HIGH PRIORITY: update vulnerable dependencies through a reviewed patch.

package.json:25 pins sharp 0.35.4. The current sharp advisory affects versions
below 0.35.5 and describes an upstream librsvg memory vulnerability, with possible
code execution under specific Linux runtime conditions. Sharp runs in server
image-processing paths. Uploaded photos pass raster/HEIC signature validation
before decoding; watermark SVGs are generated from application-owned geometry.
This review did not demonstrate attacker-controlled SVG decoding or a working
remote exploit against MyDancr. Upgrade to the patched release and verify upload,
crop, watermark, and video-poster handling.

The scan also flags source-map-js 1.2.1 through PostCSS, and braces 3.0.3 through
the ESLint globbing chain. Their observed uses are asset generation/build tooling
and linting; no customer-facing exploit path was established. Seven affected
packages represent three root advisories, not seven independent vulnerabilities.
Do not use npm audit fix --force to downgrade the Next.js lint stack blindly.

2. MEDIUM: an open customer table page can show Pending for twenty minutes.

app/internal/InternalRoster.tsx:14, 188
Guest polling uses the full-roster interval of 20 minutes. Staff requests poll
every 10 seconds, but that faster interval does not update the guest's page.
Manual refresh, focus, or returning to the visible page can update it sooner.
A component probe using the existing component and synthetic clock confirmed:
server status changed to acknowledged; UI remained Pending after 60 seconds;
the scheduled refresh showed Request seen by staff at 1,200 seconds.

Recommendation: keep slow roster refresh if desired, but provide a small,
visibility-aware active-request status refresh with the existing authorization,
cancellation, and stale-response protections. Seen must still not mean confirmed.

3. MEDIUM, GROWTH RISK: discovery silently stops at 800 profiles.

src/lib/dancr/public.ts:14-15, 109
The city and All cities queries both stop at 800, ordered by stage name and ID.
The discovery API supplies no next-page cursor or explicit truncation indicator.
Consequently, records beyond that limit cannot appear in the current directory
or its client-side filters. This audit did not establish that production has
already crossed that limit.

The response includes gallery arrays, and checked-in dancers also appear in
tonightDancers (app/api/public/discovery/route.ts:128-129). The visible homepage
refreshes discovery every 30 seconds. This is a scaling concern, not a measured
capacity failure: no production load test was performed.

Recommendation: bounded pagination, server-side filtering/counts, and a smaller
card projection; fetch gallery details when a profile is opened. Preserve prompt
visibility revocation rather than introducing broad stale public caching.

4. MEDIUM: seven existing regression assertions are out of date.

The extended selections produced these failures:

These failures did not demonstrate new privacy leaks or lost cancellation.
They do mean the broader test selection is not green. Update tests to current

ARCHITECTURE OBSERVATIONS

The app is a Next.js application with 140 API routes, 42 page components, and
226 tracked migrations. Public discovery uses an assembled legacy HTML/JS shell;
dashboards and standalone pages use React. Shared server services provide session,
role, data, and provider boundaries. This hybrid is workable but creates duplicate
UI/session integration surfaces that require careful regression coverage.

Styling is the largest maintainability concern: dancr-aesthetic.v1.css contains
14,633 lines; tracked CSS across app/src/public has 15,445 !important declarations.
The assembled shell is approximately 2.69 MB on disk, before production extraction
and compression. These are source-size measurements, not network-transfer or
render-time measurements. Consolidate styles per feature gradually, using visual
baselines; an application rewrite is not warranted by these findings.

The migration provenance guard passes. A verified schema baseline exists, but its
current plan includes 44 forward migrations and reports replayReady=false pending
forward validation. This does not mean those migrations are unapplied or broken.
It means this audit cannot certify a fresh full-schema replay or backup restore.
Do not blindly replay quarantined historical migrations against production.
